# T-018 generality audit: where the engine depends on one project

Worker run 2026-10-18, branch `agents/task-T-018`, base `claude/access-permissions-setup-ii24ws` at dabb897. Docs only: no code, rule, test or data file changed.

## Scope and method

- **Production path (audited line by line):** the import closure of `tools/urban_boq_m9.py` (the BOQ CLI), computed from the AST including function-level imports: 90 files, 43,378 lines (73 under `engine/source`, 14 under `tools`, 3 under `engine`). Every module-level constant, numeric comparison, word list, regex and layer / block / text test was read in context (four parallel readers, one per file group, merged here).
- **Outside the path (grep only):** `engine/source`, `engine`, `tools` were searched for project names (`alsenan|7757|rashed|qortuba`) and for layer / room lexicons. 69 files outside the path mention a project; they are legacy research rounds (`tools/run_round6*`, `export_round*`, `run_e1*`, `engine/freeze_manifest.py`, `engine/supervised_benchmark.py` ...) and almost all mentions are docstrings. Only the value-bearing ones are rows (403-406).
- **`rules/`:** no rule file hard-codes a project value. `rules/coverage/BOQ_FAMILY_MASTER_1.0.0.json` cites 'P7757 research' in 8 `implementation` strings (provenance text, no value). Knowledge 1.5.0 has one PROJECT_SPECIFIC rule, PS-REF-001 (service corridor is outdoors); its binding is kept out of the public registry (`PROJECT_SPECIFIC_UNBOUND`, bound in the private decision file), which is the right pattern.
- **Kinds:** LAYER_OR_NAME_DEPENDENCY (layer / block / text / room / sheet vocabularies, grammars), PROJECT_FACT (a value true of one project), TUNED_CONSTANT (a threshold with no rule id that decides what is measured, typed, released or rejected), STATED_RULE (backed by a rule id in `docs/RULES_INDEX.md`, a knowledge field or a named conventions record; listed so nobody mistakes it for tuning). Pure float epsilons and output rounding are not rows.
- Line numbers are on dabb897 and were machine-checked (every file exists, every cited line is inside the file, and a token of the value appears near the cited line; 12 drifted citations were corrected).

## Result in one view

406 rows: 292 TUNED_CONSTANT, 75 LAYER_OR_NAME_DEPENDENCY, 7 PROJECT_FACT, 32 STATED_RULE. No Alsenan coordinate, room name, region id or entity handle is used as a value in engine code; the mission's "project constant" risk lives in three places instead:

1. **One real project switch:** `tools/urban_structural_boq.py:58-63` + `tools/urban_boq_m2.py:211-216`: a structural DXF whose sha256 equals the ST7757 file is routed automatically to the frozen Alsenan adapter and conventions (route A) instead of being measured. Harmless for another villa, but it means Alsenan's structural numbers on the auto route are a replay, not a measurement (P-01).
2. **Vocabularies:** room, sheet, storey, layer and annotation word lists decide what is measured at all. Confirmed defect: `arch_rooms.py:71-110` matches in list order, BATHROOM (:73, pattern `حمام`) before POOL (:109), so the Arabic 'حمام سباحة' (swimming pool) is typed as a wet bathroom (reproduced on dabb897: `arch_rooms.room_word('حمام سباحة')` returns `('BATHROOM', 'حمام')`); `arch_v28.py:995` only patches the lost-label report (P-04). Storey lists stop at fixed names (no mezzanine / penthouse; P-05). Layer roles on the structural path come from name substrings (`drawing_inventory.py:27-41`), so a jamb line on 'DOOR-FRAME' is treated as annotation (P-03).
3. **Tuned thresholds:** about 290 constants without a rule id. The highest-risk families: the wall thickness band (0.10, 0.45) copied in seven places (P-02); opening recognition (P-09; `topology_policy.py:60` itself records that JAMB_ALLOWANCE_RATIO was set on 'the first drawing family'); seven mutually inconsistent stair detectors (P-12); constants still in drawing units that assume millimetres (P-07); and silent input caps that drop a layer without a HELD record (P-18), which breaks 'missing never becomes 0'.

Not a defect: the STATED_RULE rows (owner-approved Kuwait / owner-general values such as UP-WP-003 0.20 m upturn, UP-DOOR-MIN door +0.10 m, UP-WET-002 pan widths). Two rule-store inconsistencies were seen and are listed for the lead: UP-WP-002 means the 0.20 m upturn in the rule store (`urban_boq_m9.py:2917`) but the 0.10 m lap in the knowledge registry; `owner_finish_scope.py:245` cites URBAN-ROOF-WATERPROOF-UPTURN-200, which is not in RULES_INDEX (only in a research register).
