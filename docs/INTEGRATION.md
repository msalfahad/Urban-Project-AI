# Connecting to Urban Projects Manager (the web app)

The web app — `msalfahad/UrbanProjectsManager` — is a **Flutter + Firebase**
application. The AI system and the app share **one Firestore database**
(`urbanprojectsmanager`), so connecting them is a *write*, not an API
integration: our system writes documents; the app reads them and renders them
with no changes.

## What the app already has (and why it fits perfectly)

Inspecting the app revealed it already follows the same rule this whole system
is built on:

- **The Anthropic key already lives in Firebase Secret Manager** (`ANTHROPIC_API_KEY`),
  used by Cloud Functions in region `europe-west1`. The Flutter client never sees
  the key. Existing functions: `aiChat`, `aiAnalysis`, `aiAssist`, `aiBoqCamera`.
- The app's own code comments enforce our rule verbatim: *"The AI NEVER produces
  measurement values"* and *"numbers come FROM Firestore, not generated by the AI."*
- The app computes BOQ quantities with its own **`BoqFormulaEngine`** (Dart) from a
  `formulaType` + `measurements` map — the "code calculates" half, already built.
- Models the app currently runs: `claude-haiku-4-5` and `claude-sonnet-4-6`.

## The data model we write into

| What | Firestore path | Our writer |
|------|----------------|-----------|
| BOQ line | `projects/{projectId}/boqItems/{itemId}` | **E14 PM Sync** (`engine/pm_sync.py`) |
| Cost item | `projects/{projectId}/costItems/{itemId}` | (Phase 3) |
| Lead / enquiry | `projects/{projectId}/clientRequests/{id}` | A3 → (Phase 2) |
| Client payment | `projects/{projectId}/clientPayments/{id}` | A13 → (Phase 5) |
| AI report | `aiReports/{id}` | A8/analysis (Phase 3) |
| Audit entry | `auditLogs/{id}` | E5 Audit Log |

### `boqItems` document shape (what E14 produces)

Exactly the fields of the app's `BoqItemModel.toMap()`:

```
projectId, groupId, packageId, packageName, templateId, name, unit,
formulaType, measurements, costRate, sellingRate, isDeleted,
linkedCostItemId, notes, categoryId, costTypeId, photoUrl,
createdAt, updatedAt
```

`formulaType` ∈ `simple | area | volume | perimeter`, and the app computes:

```
area      -> length * width
volume    -> length * width * height
perimeter -> perimeter * height
simple    -> qty
```

`engine/boq_formula.py` mirrors this exactly, and `tests/test_boq_formula.py`
pins the mirror to the app's definitions so we notice if the app changes.

## What E14 PM Sync does (built, tested offline)

`engine/pm_sync.py`:

1. `measurement_to_formula(count, dimensions_m)` maps our extractor's records
   (unit + dimensions) into the app's `formulaType` + `measurements`, chosen so
   the app recomputes exactly `count * product(dimensions)`.
2. `to_boq_item_doc(line)` builds a document with exactly the app's fields.
3. `sync_boq(lines, writer)` writes each line to `projects/{projectId}/boqItems`
   through an **injectable writer** — a stub in tests, `firestore_writer(db)`
   (firebase-admin) in production.

## The one thing needed to go live

A **Firebase service-account key** for the `urbanprojectsmanager` project, placed
in the environment as a secret (never pasted in chat, never committed — already
in `.gitignore`). Then:

```python
import firebase_admin
from firebase_admin import credentials, firestore
from engine.pm_sync import sync_boq, firestore_writer

firebase_admin.initialize_app(credentials.Certificate("service-account.json"))
writer = firestore_writer(firestore.client())
sync_boq(approved_lines, writer)   # appears in the app instantly
```

## Two open decisions for the owner

1. **Where the agents run.** The app already runs its AI in **Firebase Cloud
   Functions (Node.js)** with the key in Secret Manager. Options: (a) keep the
   Python agents here as the spec + run them as a separate service that writes to
   Firestore, or (b) port the agent prompts into the existing Cloud Functions so
   everything runs in one place. Recommendation: keep building/testing in Python
   here (fast to iterate), write results to Firestore via E14; revisit (b) only
   if you want a single deployment.
2. **Model alignment.** Our agents default to `claude-opus-5`; the app runs
   `haiku-4-5` / `sonnet-4-6`. For cost, the high-volume agents (A3/A4/A5) can be
   set to match — each agent's `MODEL`/`EFFORT` constants make this a one-line
   change.
