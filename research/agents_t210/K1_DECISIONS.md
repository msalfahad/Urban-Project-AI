the risk the K1 rule protects against (a K1 / K2 shared failure, a non-stdlib dependency inside the kernel) is about
the kernel modules, which the closure check above now watches directly.

module importing a third-party package fails `tests/t210_guard_followups/test_k1_decision_record.py` (UNRECORDED) until
a record with a decision is added; a cleaned module fails it as STALE; a K1 core module that starts reaching an
offender fails it as K1_CORE_REACHES_OFFENDER.

## (b) pymupdf: NOT registered, with the reason

`engine/source/opening_height_pdf.py:84` imports `pymupdf` lazily (T-082, merge 2dee9544). PyMuPDF is AGPL-3.0 /
commercial: requirements.txt carries the Lead's licence note, PLAN_READER.md says "not PyMuPDF, AGPL", and
RESEARCH_LOG rejects AGPL libraries for the private commercial product. Adding it to
`tests/r8_0/registers/R8_0_SOURCE_DEPENDENCY_REGISTER.json` would make the engine's dependency register accept an AGPL
library: that is a licence decision, not a test fix, so it is not done. The two ids
`tests/r8_0/test_r8_0_import_boundaries.py::test_B5_B6_engine_source_dependencies_registered` and
`tests/r8_1/test_r8_1_boundaries.py::test_B5_B6_live_engine_source_dependencies_registered` stay in the known-failures
ledger (DEPENDENCY_NOT_REGISTERED). Fix proposal (its own task): OPENING_HEIGHT_PDF_V2, a new version reading the page
through a permissively licensed reader registered in B-5 first (pypdf 6.19.0 BSD is already pinned; pypdfium2 /
pdfplumber per PLAN_READER.md), proven to give the same words and segments as V1. Keeping PyMuPDF instead needs the
owner's licence decision.

Side finding: the register pins shapely `2.1.2`, requirements.txt pins `2.2.0` (the version the venv runs). The register's
`pins` block is documentation (no test reads it); not changed here (outside this row's files), noted for the Lead.

## (c) rebuild sandbox in git worktrees: FIXED (two causes, the second hidden by the first)

`tests/christiannp_blind_process/test_package.py::test_builder_reproduces_outputs_byte_for_byte` (ledger
WORKTREE_GITDIR) failed in every agent checkout because every checkout here is a git worktree.

1. Cause 1 (T-202): `tests/rebuild_sandbox.py` wrote `gitdir: <root>/.git` into the copy; in a worktree `<root>/.git` is
   a FILE, so git failed and the builder stamped `UNCOMMITTED`. Fix: `_git_dir(root)` follows the `gitdir:` line of a
   `.git` file (relative paths from the root; a `.git` file without that line is refused).
2. Cause 2 (found after fixing 1, masked until then): with git working, the builder's `git log -1 --format=%h` gave
   `680264de` where the package records `680264d`: the SAME commit, but core.abbrev=auto lengthens `%h` as the
   repository grows (24,302 packed objects now). Fix: for `git=True` only, the sandbox pins `core.abbrev=7` (git's
   minimum, the length every committed stamp was written with) through `GIT_CONFIG_COUNT`, keeping the caller's other
   `GIT_CONFIG_*` entries; git still lengthens an abbreviation that would be ambiguous. `git=False` builders get the
   caller's environment unchanged.

Proof: the old helper in a synthetic worktree stamps `UNCOMMITTED` (normal checkout: the commit); the new helper gives
the commit in both, at 7 characters even when the caller asks for 12 (tests/t210_guard_followups/
test_rebuild_sandbox_git.py, 7 tests). The christiannp rebuild test passes on the task tree. The committed christiannp
package is unchanged (the test compares against it).
